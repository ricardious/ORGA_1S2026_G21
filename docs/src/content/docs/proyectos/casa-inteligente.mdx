## Resumen

El proyecto final del curso consistió en construir una **maqueta de casa inteligente** capaz de controlar cinco ambientes de iluminación, un ventilador DC y una puerta automatizada con servomotor.

El sistema se apoya en un **Arduino Uno** como unidad central, usa la **EEPROM interna** para persistir escenas, una **pantalla LCD I2C** para retroalimentación local, una **aplicación de escritorio** que carga configuraciones `.org` por USB y una **aplicación móvil** que activa modos por Bluetooth clásico.

A diferencia de las prácticas anteriores —resueltas con lógica discreta— aquí el eje del trabajo es la **organización de la memoria**: cómo se estructura una escena, en qué dirección vive, cuándo se escribe y cómo se valida antes de persistirla.

## Requisitos funcionales

### Control de escenas

El sistema maneja cinco escenas: `modo_fiesta`, `modo_relajado`, `modo_noche`, `encender_todo` y `apagar_todo`. Cada escena almacena estado del ventilador, patrón de LEDs y mensaje para el LCD.

### Persistencia en EEPROM

Cada escena se guarda en una dirección fija mediante una estructura de **36 bytes**:

| Campo | Tamaño | Función |
|---|---:|---|
| `magic` | 1 byte | Firma `0x42` que marca la escena como válida |
| `fan` | 1 byte | Estado del ventilador (`FAN_ON` / `FAN_OFF`) |
| `ledPattern` | 1 byte | Patrón de iluminación (`OFF`, `ON`, `ALTERNATING`) |
| `message` | 33 bytes | Texto que se muestra en el LCD |

La escritura ocurre **únicamente cuando una carga `.org` finaliza correctamente**. No hay siembra de valores por defecto al arrancar: si la EEPROM nunca recibió una configuración, la firma no coincide y el sistema reporta el modo como no configurado.

### Control remoto por Bluetooth y serial

El sketch procesa los comandos entrantes de forma idéntica vengan del monitor serial o del módulo HC-06:

| Comando | Efecto |
|---|---|
| `modo_fiesta` | Aplica la escena de fiesta (LEDs alternándose) |
| `modo_relajado` | Aplica la escena relajada |
| `modo_noche` | Aplica la escena nocturna |
| `encender_todo` | Enciende las cinco zonas |
| `apagar_todo` | Apaga las cinco zonas |
| `estado` | Devuelve `STATUS:<modo>:<OK\|ERROR>` por serial |
| `abrir_puerta` | Lleva el servomotor a 90° |
| `cerrar_puerta` | Lleva el servomotor a 0° |

### Retroalimentación local

- LCD I2C 16x2 con mensaje del modo y estado del ventilador.
- LED **azul**: sistema listo.
- LED **verde**: carga exitosa (parpadea tres veces).
- LED **rojo**: error de configuración o de carga.

### Actuadores y salidas

- Cinco salidas de iluminación: sala, comedor, cocina, baño y habitación.
- Un motor DC para el ventilador.
- Un servomotor para apertura y cierre de puerta.
- Un botón físico con *debounce* de 40 ms para alternar la puerta.

## Arquitectura de la solución

### Descripción general

La arquitectura se divide en tres capas operativas:

1. **Unidad central Arduino**: recibe comandos por serial, administra la EEPROM y controla las salidas físicas.
2. **Interfaz de escritorio**: prepara y transmite archivos `.org` al Arduino por USB.
3. **Interfaz móvil**: envía comandos por Bluetooth clásico para activar modos o consultar estado.

### Flujo general del sistema

| Origen | Destino y función |
|---|---|
| Archivo `.org` | App de escritorio → Serial USB → Arduino → EEPROM |
| Teléfono Android | Bluetooth HC-06 → Arduino → luces, LCD, ventilador y puerta |
| EEPROM | Arduino → recuperación y aplicación del modo activo |

La lógica del sistema permanece concentrada en el Arduino: allí se validan escenas, se escriben datos en EEPROM y se activan luces, ventilador y puerta. Las aplicaciones son solo capas de transporte.

### Bloques de software

| Componente | Tecnología | Función |
|---|---|---|
| `EEPROM_Liquid_Controller` | Python + Tkinter | Selección de puerto, carga de archivo `.org` y envío serial |
| `eeprom_liquid_remote` | Flutter | Conexión Bluetooth y envío de comandos de modo |
| Sketch Arduino | C++ para Arduino | Procesamiento central, EEPROM, LCD, luces, ventilador y puerta |

## Formato del archivo `.org`

### Sintaxis reconocida

- El archivo debe iniciar con `conf_ini`.
- Debe cerrar con `conf:fin`.
- Los comentarios usan `//`.
- Cada modo se declara por su nombre en una línea propia.
- Para cada modo deben declararse `Ventilador:` y `LED'S:`.
- `Mensaje en LCD:` es opcional; si no aparece, el sistema usa un mensaje por defecto.

La validación se hace durante la lectura serial, **línea por línea**. Así, cuando aparece un error, el sistema puede marcarlo enseguida en el LCD, en el LED rojo y en la salida serial, sin esperar a que termine la transferencia.

```cpp
void processLine(String rawLine) {
  String line = stripComment(rawLine);
  line.trim();
  if (line.length() == 0) return;

  if (line == "conf_ini") {
    beginUpload();
    return;
  }

  if (uploadActive) {
    processUploadLine(line);
    return;
  }

  processCommand(line);
}
```

Esa función es la bisagra del sistema: separa el **modo de carga** del **modo de comandos**. Mientras `uploadActive` esté en alto, una línea como `modo_fiesta` no activa la escena, sino que abre su definición.

### Valores válidos

| Campo | Valores reconocidos |
|---|---|
| Modo | `modo_fiesta`, `modo_relajado`, `modo_noche`, `encender_todo`, `apagar_todo` |
| `Ventilador:` | `ON`, `OFF` |
| `LED'S:` | `ON`, `OFF`, `Alternandose` |

### Ejemplo completo

Este es el archivo de referencia incluido en el repositorio (`examples/modos_completos.org`):

### Errores detectados

La carga se cancela por completo si el sketch detecta cualquiera de estas condiciones:

| Motivo reportado | Causa |
|---|---|
| `modo no definido` | Aparece un atributo antes de declarar el modo al que pertenece |
| `modo incompleto` | Un modo se cierra sin `Ventilador:` o sin `LED'S:` |
| `linea invalida` | La línea no corresponde a ningún modo ni atributo conocido |
| `ventilador invalido` | Valor distinto de `ON` u `OFF` |
| `leds invalido` | Valor distinto de `ON`, `OFF` o `Alternandose` |
| `archivo vacio` | Se recibió `conf:fin` sin ningún modo declarado |

Cuando esto ocurre, **no se escribe nada en EEPROM**: la configuración previa queda intacta.

```cpp
void failUpload(const char *reason) {
  uploadActive = false;
  currentUploadMode = NO_MODE;
  systemError = true;
  digitalWrite(led_azul, LOW);
  digitalWrite(led_verde, LOW);
  digitalWrite(led_rojo, HIGH);
  showLcd("Error archivo", reason);
  Serial.print("UPLOAD_ERROR:");
  Serial.println(reason);
}
```

## Mapa de direcciones EEPROM

Cada escena ocupa 36 bytes y arranca en una dirección constante definida de forma literal en el sketch. Los valores de la última columna son los que escribe el archivo de referencia, no valores precargados de fábrica.

| Modo | Dirección | Ventilador | LEDs | Mensaje |
|---|---:|:---:|:---:|---|
| `modo_fiesta` | 0 | ON | Alternándose | `Modo: FIESTA.` |
| `modo_relajado` | 36 | OFF | OFF | `Modo: RELAJADO.` |
| `modo_noche` | 72 | OFF | OFF | `Modo: NOCHE.` |
| `encender_todo` | 108 | ON | ON | `Modo: TODO ON.` |
| `apagar_todo` | 144 | OFF | OFF | `Modo: TODO OFF.` |

```cpp
const int EEPROM_ADDR_FIESTA = 0;
const int EEPROM_ADDR_RELAJADO = 36;
const int EEPROM_ADDR_NOCHE = 72;
const int EEPROM_ADDR_ENCENDER_TODO = 108;
const int EEPROM_ADDR_APAGAR_TODO = 144;
```

La escritura persistente se hace sobre esas posiciones mediante `EEPROM.put()` usando la estructura `SceneConfig`, de modo que cada modo conserva su configuración incluso después de reiniciar el Arduino.

```cpp
void writeSceneToEeprom(byte mode, PendingScene scene) {
  SceneConfig stored;
  stored.magic = EEPROM_MAGIC;
  stored.fan = scene.fan;
  stored.ledPattern = scene.ledPattern;
  copyMessage(String(scene.message), stored.message);
  EEPROM.put(eepromAddress(mode), stored);
}
```

El campo `magic` (`0x42`) es lo que permite distinguir una escena real de memoria sin inicializar. Si no coincide, `applyMode()` no enciende nada y muestra `Modo sin config` en el LCD.

## Fragmentos clave del código

### Aplicación de escenas

`applyMode()` enlaza EEPROM, LEDs de estado, LCD, ventilador e iluminación. Primero valida que la escena leída tenga firma correcta, luego actualiza el estado general del sistema y finalmente activa las salidas físicas.

```cpp
void applyMode(byte mode) {
  SceneConfig scene = readSceneFromEeprom(mode);
  if (scene.magic != EEPROM_MAGIC) {
    systemError = true;
    digitalWrite(led_rojo, HIGH);
    showLcd("Modo sin config", modeName(mode));
    return;
  }

  activeMode = mode;
  systemError = false;
  digitalWrite(led_rojo, LOW);
  digitalWrite(led_azul, HIGH);
  digitalWrite(motor_ventilador, scene.fan == FAN_ON ? HIGH : LOW);
  applyLedPattern(scene.ledPattern);
  showLcd(scene.message,
          scene.fan == FAN_ON ? "Ventilador ON" : "Ventilador OFF");
}
```

### Persistencia de escenas

La escritura en EEPROM se realiza al finalizar correctamente la carga. Solo se persisten los modos efectivamente declarados en el archivo (`touched`), de modo que un `.org` parcial no borra las escenas restantes.

```cpp
void finishUpload() {
  if (!commitCurrentUploadMode()) {
    failUpload("modo incompleto");
    return;
  }

  for (byte i = 0; i < MODE_COUNT; i++) {
    if (pendingScenes[i].touched) {
      writeSceneToEeprom(i, pendingScenes[i]);
    }
  }
}
```

### Comandos operativos

Además de aplicar modos, el sketch soporta comandos puntuales que no requieren recargar la configuración completa.


## Pruebas y validación

### Protocolo serial observable

El sistema es verificable desde el monitor serial sin necesidad de instrumentación adicional, porque cada transición publica una línea:

| Salida serial | Significado |
|---|---|
| `READY` | El sistema arrancó y espera comandos |
| `STATUS:<modo>:OK` | Respuesta a `estado` con la escena activa |
| `STATUS:<modo>:ERROR` | Hay un error de configuración vigente |
| `UPLOAD_ERROR:<motivo>` | La carga `.org` se canceló, con la causa |

### Casos de validación ejecutados

| Caso | Condición | Resultado esperado |
|---|---|---|
| Arranque en frío | EEPROM sin configurar | LCD muestra `Modo sin config` al pedir un modo |
| Carga válida completa | `modos_completos.org` | LED verde parpadea 3 veces, LCD `Configuracion guardada` |
| Carga parcial | `modo_fiesta.org` | Solo se sobrescribe la escena de fiesta |
| Modo incompleto | Modo sin `LED'S:` | `UPLOAD_ERROR:modo incompleto`, EEPROM intacta |
| Valor inválido | `Ventilador: TAL VEZ` | `UPLOAD_ERROR:ventilador invalido` |
| Persistencia | Reinicio tras carga válida | Las escenas siguen disponibles sin recargar |
| Control remoto | Comando por HC-06 | Misma respuesta que por USB |
| Puerta manual | Pulsación del botón físico | Alterna 0° / 90° sin rebotes |

### Hallazgos

- Separar la validación de la escritura fue determinante: al escribir solo en `finishUpload()`, un archivo mal formado nunca deja la EEPROM en estado inconsistente.
- Eliminar la siembra de valores por defecto hizo el comportamiento más honesto: un modo sin configurar se reporta como tal en vez de simular una escena que nunca se cargó.
- El patrón alternado con `millis()` evitó bloquear el bucle, lo que mantiene la puerta y los comandos remotos con respuesta inmediata durante el modo fiesta.

## Conclusiones

- El proyecto integra configuración externa, persistencia en EEPROM, control remoto y visualización local en un solo sistema coherente.
- La separación entre Arduino, aplicación de escritorio y aplicación móvil ordena el funcionamiento: el microcontrolador concentra la lógica y las apps son solo transporte.
- Validar durante la transferencia y escribir solo al final es lo que hace confiable la persistencia: ningún archivo inválido corrompe la configuración vigente.
- El uso de direcciones fijas y una firma de validez convierte a la EEPROM en una estructura de datos legible, no en un volcado opaco de bytes.
- La maqueta física demuestra la integración completa entre electrónica, mecánica y las tres capas de software.
